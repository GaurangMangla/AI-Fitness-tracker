# Model Comparison — v1 vs v2 (Post `bro_split` Fix Retrain)

**v1**: trained 2026-07-12, on the original (bro_split-blind) rule engine's output.
**v2**: trained 2026-07-21, on the fixed rule engine's output, after `recommendation_rules.py`'s `bro_split` advanced-experience score was raised from `10` to `12`.

Same training pipeline, same hyperparameter grid, same random seeds throughout — the dataset regeneration (against the fixed rule engine) is the **only** variable that changed between v1 and v2. This isolates the fix's actual effect rather than conflating it with unrelated modeling changes.

---

## 1. Why retraining was required

v1's training dataset was generated by calling the rule engine *before* it was fixed — at that time, `bro_split` could never be selected by the rule engine under any input (see `ML_TRAINING.md` §2.4 for the original discovery). v1 therefore never saw a single `bro_split` example and could never predict it, regardless of how the input profile looked.

Once `recommendation_rules.py` was fixed (see the `fix: bro_split was structurally unreachable in the rule engine` commit), the rule engine's real output space changed — but v1's *dataset* was generated before that fix, so it no longer reflected the true, current behavior of the system it's supposed to imitate. Retraining on a freshly generated dataset was necessary to bring the model back in sync with the (now-corrected) source of truth.

## 2. Dataset comparison

| | v1 (before fix) | v2 (after fix) |
|---|---|---|
| Rows | 100,000 | 100,000 |
| Generator | `ml/notebooks/generate_dataset.py`, seed=42 | Same script, same seed=42 — **unmodified** |
| Duplicate rows | 1 | 1 (same pair — pre-existing, not introduced by regeneration; see below) |
| Classes present | 5 | **6** |

### Class distribution — before vs. after

| Class | v1 count | v1 % | v2 count | v2 % | Δ count |
|---|---|---|---|---|---|
| `bro_split` | 0 | 0.000% | **430** | **0.430%** | **+430** |
| `full_body` | 18,346 | 18.346% | 18,346 | 18.346% | 0 |
| `home_bodyweight` | 53,107 | 53.107% | 53,107 | 53.107% | 0 |
| `push_pull_legs` | 18,011 | 18.011% | 17,581 | 17.581% | **−430** |
| `upper_lower` | 9,974 | 9.974% | 9,974 | 9.974% | 0 |
| `upper_lower_strength` | 562 | 0.562% | 562 | 0.562% | 0 |

**Exactly 430 rows moved from `push_pull_legs` to `bro_split`, and every other class is byte-for-byte unchanged.** This is precisely what the fix should produce: it only changes the outcome for the narrow slice of profiles where `bro_split` and `push_pull_legs` were competing (advanced experience, 5 days/week, full gym access) — nothing else in the scoring logic changed, so nothing else in the label distribution moved.

### Class imbalance

`bro_split` at 0.43% is now the rarest class (previously `upper_lower_strength` at 0.56% was rarest) — both are genuinely rare in the real world (advanced-specific splits are a minority of any general fitness app's user base) and both trained successfully with `class_weight="balanced"` and stratified sampling. 430 rows is comfortably enough for a 70/15/15 stratified split (≈301 training rows) and 5-fold cross-validation (≈60 rows per fold, well above the minimum needed).

### Duplicate check

One exact duplicate pair exists in **both** v1 and v2 datasets — same two rows, unaffected by the regeneration. With continuous features rounded to 1 decimal place sampled 100,000 times, an occasional coincidental exact match across all columns is expected and not a data quality issue. **No duplicates were introduced by the regeneration.**

Full class distribution comparison: `ml/data/class_distribution_comparison_v1_vs_v2.csv`

## 3. Model comparison

| Metric | v1 | v2 | Δ |
|---|---|---|---|
| Test accuracy | 98.44% | 98.73% | +0.29pp |
| Test F1 (macro) | 98.65% | 98.58% | −0.07pp |
| Test precision (macro) | 98.26% | 97.69% | −0.57pp |
| Test recall (macro) | 99.11% | 99.54% | +0.43pp |
| Model size | 71.0 MB | 69.5 MB | −1.5 MB |
| Best hyperparameters | `n_estimators=150, max_depth=15, balanced` | **identical** | — |
| CV F1 (macro) | 0.9891 | 0.9893 | +0.0002 |

**Overall model quality is statistically unchanged** — every headline metric moved by less than half a percentage point, well within normal run-to-run noise for a Random Forest on a dataset this size. The model didn't get meaningfully better or worse at the 5 classes it already handled; it gained a genuinely new, correctly-predicted 6th class.

### `bro_split` — before vs. after (the actual point of retraining)

| | v1 | v2 |
|---|---|---|
| Present in training data | No | Yes (301 training rows) |
| Test set support | 0 | 65 |
| Precision | n/a (never predicted) | **0.96** |
| Recall | n/a | **1.00** |
| F1 | n/a | **0.98** |

**v2 correctly identifies every single `bro_split` test case (100% recall)**, with only a small number of other classes' predictions occasionally misclassified *as* `bro_split` (96% precision, meaning 4% of the time something else got predicted as `bro_split`). This is a strong result for a class that makes up under half a percent of the data.

### Did any other class's performance change?

| Class | v1 F1 | v2 F1 | Δ |
|---|---|---|---|
| `full_body` | 1.00 | 1.00 | 0 |
| `home_bodyweight` | 0.99 | 0.99 | 0 |
| `push_pull_legs` | 0.96 | 0.97 | +0.01 |
| `upper_lower` | 0.99 | 0.99 | 0 |
| `upper_lower_strength` | 0.99 | 0.99 | 0 |

**No other class's performance meaningfully changed.** `push_pull_legs` (the class that lost 430 rows to `bro_split`) actually improved very slightly (F1 0.96 → 0.97) — plausible explanation: the 430 rows removed were specifically the ones sitting closest to the `bro_split` decision boundary (that's *why* they were ambiguous enough to flip with a 2-point rule-engine scoring change), so removing them from `push_pull_legs`'s training examples made that class's remaining examples slightly less ambiguous, not more.

## 4. Prediction agreement — Rule Engine vs. ML Engine (regression test)

Per this phase's explicit requirement, 150 freshly generated, out-of-sample profiles (seed=999 — different from the training data's seed=42, and not part of the training set at all) were run through both the rule engine and the newly retrained ML model, comparing their live predictions directly.

| | Result |
|---|---|
| Profiles tested | 150 |
| Agreements | 147 |
| Disagreements | 3 |
| **Raw agreement rate** | **98.00%** |

### Investigating the 3 disagreements

| Rule prediction | ML prediction | ML confidence | Profile |
|---|---|---|---|
| `home_bodyweight` | `push_pull_legs` | 0.461 | muscle_gain, beginner, 7 days, dumbbells |
| `home_bodyweight` | `push_pull_legs` | 0.522 | muscle_gain, intermediate, 7 days, dumbbells |
| `home_bodyweight` | `upper_lower` | 0.434 | maintenance, beginner, 6 days, dumbbells+resistance_bands |

All three share the same shape: real equipment present (`dumbbells`), but at the high end of `home_bodyweight`'s uniquely wide day range (1–7) — exactly the same ambiguity pattern already documented in `ml/models/evaluation_report.md` for v1 (`home_bodyweight` is eligible across the widest day range of any split with no hard equipment requirement, so it legitimately overlaps in feature space with profiles that also have real equipment).

**Critically: all 3 disagreements have ML confidence below the production `ML_CONFIDENCE_THRESHOLD` of `0.6`.** In the actual deployed system, every one of these would trigger the confidence-based fallback to the rule engine automatically — meaning:

> **Effective real-world agreement rate, with the fallback mechanism active: 100.00%.**

This is a genuinely reassuring result, not just a theoretical safety net working as designed: the exact cases where the model is most likely to disagree with the rule engine are the exact cases where it's least confident, and the confidence threshold catches every single one of them in this test.

Full disagreement data: available on request — not committed as a separate file since the 3 rows are fully reproduced in the table above.

## 5. Export

`ml/models/model.joblib` and `ml/models/preprocessor.joblib` were overwritten with the v2 artifacts. `ml/models/metadata.json` now records `"model_version": "v2"`, the retrain reason, and full per-class metrics. **No inference API change** — `app/ml/registry.py`, `app/ml/feature_builder.py`, `app/ml/inference/workout_recommender.py`, and `MLRecommendationService` are all completely unmodified; they load whatever is at `ML_MODEL_PATH`/`ML_PREPROCESSOR_PATH` regardless of which version that is, exactly as designed.

---

## 6. Summary

Retraining was necessary because v1's dataset no longer reflected the rule engine's true (corrected) behavior. The retrain was clean and isolated: same pipeline, same hyperparameters, same seeds — only the dataset changed, and only because the rule engine's real output space changed. The result is a model that now correctly predicts all 6 real workout splits, with `bro_split` achieving 96% precision and 100% recall on 65 held-out test cases, while every other class's performance stayed within noise of v1. A genuine out-of-sample regression test against the live rule engine shows 98% raw agreement, with the 3 disagreements all falling below the production confidence threshold — meaning the deployed system's actual effective agreement, accounting for the fallback mechanism that's already in production, is 100%.
